## Findings

- [T-001] Dinur-Nissim reconstruction theory: if answers to many subset-sum queries carry noise smaller than about sqrt(n), an efficient attacker can reconstruct most records, so per-query accuracy and total query count must be traded off and cannot be fixed by rate limits alone | https://differentialprivacy.org/reconstruction-theory/ | high | n/a | retrieved 2026-10-26 | status: unreviewed
- [T-002] Evidence against ad hoc defenses: a study cited in a reconstruction-attack overview found defenses were either equivalent to differential privacy or ad hoc and tailored to one attack with no guarantee against others; the US Census Bureau judged reconstruction a practical danger and adopted DP for 2020 (at a real utility cost, which Alabama litigated) | https://en.wikipedia.org/wiki/Reconstruction_attack | low | US | retrieved 2026-10-26 | status: unreviewed
- [T-003] Adaptive attacks (gradient, RL, search, human red-teaming) bypassed 12 published prompt-injection and jailbreak defenses with over 90 percent success for most, though those defenses had reported near-zero success; so a gateway cannot rely on an LLM-level filter alone against a buyer agent trying to extract raw data (USENIX Security 2026) | https://arxiv.org/abs/2510.09023 | high | n/a | retrieved 2026-10-26 | status: unreviewed
- [T-004] RAG-Thief: an agent-driven attack that starts from one adversarial query and generates follow-ups from the replies recovered over 70 percent of a private RAG knowledge base (incl. GPTs and Coze); this is the exact threat of a buyer agent draining a seller KB via many legitimate-looking queries (self-reported results) | https://arxiv.org/abs/2411.14110v1 | med | n/a | retrieved 2026-10-26 | status: unreviewed
- [T-005] RAGCrawler (2026) models extraction as adaptive coverage: it builds a knowledge graph of what it has already seen and plans benign-looking queries toward unretrieved regions, and the authors say earlier multi-turn attacks stalled after a few rounds; this defeats naive per-query filters and simple repetition detection (self-reported) | https://arxiv.org/html/2601.15678v1 | med | n/a | retrieved 2026-10-26 | status: unreviewed
- [T-006] TEE.fail (Oct 2025): a sub-1000 USD DDR5 memory-bus interposer extracted keys, in some cases attestation keys, from Intel SGX/TDX and AMD SEV-SNP with Ciphertext Hiding, and the keys could be used against Nvidia GPU confidential computing; needs physical access plus root, and Intel and AMD call physical attacks out of scope. Implication: a TEE does not protect the seller's data from a malicious or compromised host operator, so the gateway host must be the seller or a trusted party (news coverage only, paper not fetched) | https://thehackernews.com/2025/10/new-teefail-side-channel-attack.html | med | n/a | retrieved 2026-10-26 | status: unreviewed
- [T-007] MCPTox benchmark: tool-description poisoning on real MCP servers is a different and more effective injection vector than the tool-result payloads tested in AgentDojo and InjecAgent; seller-supplied tool metadata can hijack a buyer agent even if the tool is never called | https://arxiv.org/html/2508.14925v1 | med | n/a | retrieved 2026-10-26 | status: unreviewed
- [T-008] MCP-ITP: automated implicit tool poisoning reached up to 84.2 percent attack success across 12 LLM agents on MCPTox with detectors catching as little as 0.3 percent; the poisoned description steers the agent into misusing a legitimate high-privilege tool. Direct risk for a seller-hosted MCP endpoint that a buyer agent connects to | https://arxiv.org/pdf/2601.07395 | med | n/a | retrieved 2026-10-26 | status: unreviewed
- [T-009] MCP spec says clients MUST treat tool annotations as untrusted unless from a trusted server, recommends a human in the loop, and makes authorization OPTIONAL (OAuth 2.1 when used, token audience validation required); there is no built-in protection against a malicious seller server, so the buyer-side defense is policy outside the protocol. Also no payment or metering primitive in the spec | https://modelcontextprotocol.io/specification/2025-11-25/basic/authorization | high | n/a | retrieved 2026-10-26 | status: unreviewed
- [T-010] MCP docs state results from one server are untrusted input to another server's tools and that tool names and descriptions can carry hidden steering instructions; a buyer agent connected to multiple sellers needs isolation between them | https://modelcontextprotocol.io/docs/2026-07-28/develop/clients/client-best-practices | med | n/a | retrieved 2026-10-26 | status: unreviewed
- [T-011] Industry DP tooling survey: most tools only track (odometer) the privacy budget and few enforce it by blocking queries (OpenDP, Tumult do), and none handle growing datasets; a pay-per-query gateway with a growing KB would need custom budget accounting. Evidence against off-the-shelf DP for this use | https://arxiv.org/pdf/2211.03898 | med | n/a | retrieved 2026-10-26 | status: unreviewed
- [T-012] Apple-style local DP deployments showed a per-day budget of 16 compounds to a weak guarantee within days and headline epsilon figures degrade under composition; the paper warns of privacy-washing, so any claimed epsilon for a metered query service must be accounted cumulatively per buyer | https://arxiv.org/pdf/2511.06305 | med | n/a | retrieved 2026-10-26 | status: unreviewed
- [T-013] AWS Clean Rooms DP limits: works only on S3 data, needs a user identifier column, no subqueries, only COUNT/SUM/AVG/STDDEV style aggregates at user level, and no joins across two DP providers; aggregation rules offer minimum thresholds. Clean-room controls fit statistical aggregates over user rows, not free-form natural-language answers about unstructured experiment knowledge | https://docs.aws.amazon.com/clean-rooms/latest/userguide/custom-diff-privacy.html | high | n/a | retrieved 2026-10-26 | status: unreviewed
- [T-014] Architecture trade-off (low confidence, vendor blogs): clean rooms centralise copies of contributed data in a neutral venue, federated setups move computation to the data but still leak via updates and need secure aggregation, DP or TEEs, and federated queries add latency. Data residency or transfer law may favor federated for a seller wanting data to stay in India (links to cross-border legal question L-009) | https://lifebit.ai/blog/why-a-federated-analytics-platform-is-the-ultimate-data-peace-treaty/ | low | n/a | retrieved 2026-10-26 | status: unreviewed
- [T-015] Gap: no source found showing query auditing (simulatable auditors) or rate limits and output caps working against an adaptive LLM-agent extractor on unstructured knowledge; defenses against RAG extraction like T-004 and T-005 remain unevaluated by independent work in my results | https://arxiv.org/html/2510.02964v1 | low | n/a | retrieved 2026-10-26 | status: unreviewed
- [T-016] x402 (Coinbase CDP docs): the server answers an unpaid request with a payment-required response giving price, recipient and accepted options; the client signs a payment and resends; a facilitator verifies, the server does the work, then the facilitator settles and the resource is returned. Pricing modes include a fixed price, a maximum authorization with settlement only for actual usage, or batched deferred settlement, which fits per-query billing where answer cost varies. Docs do not state fees or settlement finality | https://docs.cdp.coinbase.com/x402/core-concepts/how-it-works | med | n/a | retrieved 2026-10-26 | status: unreviewed
- [T-017] x402 settles mainly in USDC on EVM chains and Solana (other ERC-20 or SPL tokens possible) via a facilitator; a seller or buyer in India would depend on stablecoin or crypto rails, so a legal question exists on Indian crypto-asset tax and RBI/FEMA treatment of cross-border stablecoin payments (analyst inference, not checked; links to Legal questions on cross-border payments). Docs say CDP has processed over 100 million x402 payments (vendor claim) | https://docs.cdp.coinbase.com/x402/welcome | med | India | retrieved 2026-10-26 | status: unreviewed
- [T-018] AP2 (Google Agent Payments Protocol) repo is code samples and demos with Pydantic and JSON-schema objects, a human-present card payment scenario, no stated spec version, and no published PyPI package; mandates, supported rails and x402 relation are not described on the repo page. Secondary press describes signed Intent and Cart mandates, but the primary page does not confirm this. Treat AP2 as early-stage and consumer-checkout oriented rather than B2B per-query data metering | https://github.com/google-agentic-commerce/AP2 | low | n/a | retrieved 2026-10-26 | status: unreviewed
- [T-019] Independent RAG extraction benchmark (KDD 2026 D&B track, arXiv 2602.09319) tested four defenses (LLM query-block classifier, retrieval similarity threshold, system-prompt refusal, summarisation instruction). Conclusion: no single defense gives complete protection. Similarity threshold was strongest, with thresholds of 0.5 to 0.7 pushing retrieval extraction near zero but cutting recall; the query classifier and prompt refusal fail against IKEA, an attack with no overt extraction intent. Evidence that cheap output-side controls help but leak against benign-looking queries | https://arxiv.org/html/2602.09319 | med | n/a | retrieved 2026-10-26 | status: unreviewed
- [T-020] Same benchmark (follow-up to T-015): the paper has no formal adaptive evaluation against each defense, but shows attackers can stay semantically close to legitimate queries to pass thresholds, and adding query diversity raised retrieval extraction (DGEA 24.0 to 30.4, R-EB 28.7 to 36.8) under the threshold defense. Only first 100k of 143k characters read. So defenses are only partly evaluated and the independent-evaluation gap in T-015 is narrowed, not closed | https://arxiv.org/html/2602.09319 | med | n/a | retrieved 2026-10-26 | status: unreviewed
- [T-021] Primary TEE.fail project page (refines T-006): DDR5 interposer under 1000 USD defeats Intel SGX/TDX (4th-gen Xeon onward) and AMD SEV-SNP on Zen 4 and Zen 5 because memory encryption is deterministic; researchers extracted Intel's Provisioning Certification Key and forged SGX/TDX quotes that passed DCAP verification at the highest trust level with invalid measurements. Page does not say root is required (T-006 said root; unconfirmed). Intel (advisory 2025-10-28) and AMD (AMD-SB-3040) treat interposers as out of scope and AMD plans no firmware fix. Not seen exploited in the wild | https://tee.fail | high | n/a | retrieved 2026-10-26 | status: unreviewed
- [T-022] TEE.fail page advises not trusting attestation reports without knowing the physical location of the machine, securing servers physically, and factoring TEE compromise into the design. Implication for a gateway: remote attestation shown to a seller proves little if the buyer or a third-party cloud controls the hardware, so confidential computing only helps if the host is physically controlled by the seller or a trusted operator; this favors a seller-hosted (federated) deployment for high-value data (analyst inference) | https://tee.fail | med | n/a | retrieved 2026-10-26 | status: unreviewed
- [T-023] Stripe docs: basic usage-based billing is built on the Meters API, but Stripe now recommends Metronome (acquired by Stripe) for new usage-based integrations, including prepaid credits, real-time usage visibility and high-volume ingestion. These tools bill account-holding customers on invoices or credits, so they suit an enterprise buyer with a contract, whereas x402 suits accountless pay-per-call; a gateway could need both. Vendor docs, plan details may change | https://docs.stripe.com/billing/subscriptions/usage-based | med | n/a | retrieved 2026-10-26 | status: unreviewed
- [T-024] Builder guides (low confidence, not primary) describe gating only the MCP tools/call on priced tools behind x402 middleware while leaving tools/list free, with the facilitator checking signature and replay protection. This shows per-call monetization of MCP tools is being built in practice, although T-009 shows the MCP spec itself has no payment primitive; claimed adoption figures in these guides are unverified | https://www.alchemy.com/overviews/how-to-add-x402-payments-to-an-mcp-server | low | n/a | retrieved 2026-10-26 | status: unreviewed
- [T-025] DP-SynRAG (arXiv 2510.06719) states that existing private RAG methods use query-time DP, which needs repeated noise injection and accumulates privacy loss with every query; it proposes generating a differentially private synthetic text database once so it can be reused at a fixed privacy budget, claiming better utility than prior private RAG (abstract only, no numbers seen). Partial answer to the open question on DP for free text: synthetic-corpus DP avoids per-query budget burn but the buyer then queries a lossy synthetic copy, which may defeat the value of selling real unused-experiment findings (analyst inference) | https://arxiv.org/abs/2510.06719 | med | n/a | retrieved 2026-10-26 | status: unreviewed
- [T-026] Evidence on Census DP (supersedes the weak source for T-002): a peer-reviewed-style critique (Muralidhar and Ruggles, arXiv 2407.15957) says the Bureau declared in 2017 that data swapping carried high disclosure risk and committed to DP for 2020, but argues the 2010 risk assessment was overstated and demonstration DP products had poor utility, concluding the 2020 release offers neither privacy nor accuracy. This is a contested claim, not settled; it shows DP's utility cost is real and disputed. Did not retrieve a Bureau primary document (its PDF was unreadable) | https://arxiv.org/abs/2407.15957 | med | US | retrieved 2026-10-26 | status: unreviewed
- [T-027] Query-stream anomaly detection: a June 2026 paper (arXiv 2606.05725) tests whether a window of embedded API queries deviates from benign traffic using MMD, reporting 0.3 percent false positives and 100 percent detection on pure attacker traffic (90.5 percent across mixed attacker fractions) on 14 attacker-normal pairs across 4 model-extraction scenarios. It targets model extraction, not KB extraction, the abstract reports no adaptive-attacker test, and the set is small; another result set notes passive detection acts only after extraction has begun. So anomaly detection is promising but unproven against RAGCrawler-style adaptive agents (T-005); self-reported | https://arxiv.org/abs/2606.05725 | low | n/a | retrieved 2026-10-26 | status: unreviewed
